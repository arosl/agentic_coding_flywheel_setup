# Known non-herdr divergences

Related: [index](../index.md), `AGENTS.md` ("Scope", "Upstream sync")

Fork-only changes to upstream files, other than the herdr port, Incus first with Docker optional, and the supported platforms, which are why the fork exists ("Scope" in `AGENTS.md`). At each upstream sync, resolve each entry knowingly, and drop it once upstream fixes it. Each entry names its bead.

- acfs-gxd: test fixes that make the gate pass: tests assert the upgrade paths upstream retired, and `test_release_doctor.sh` fakes the version check unless a test clears it (release-doctor's missing-`install.sh` fix and its test are upstream's since the 2026-10-10 sync).
- acfs-bnz: CI pins shellcheck 0.9.0 and bun, which upstream's CI leaves unpinned.
- acfs-0pj: the plugin-pack tests set their fixtures' file modes, because upstream's tests fail under umask 0002.
- acfs-rst: `test_swarm_fleet_probe.py` also sets its library fixtures' modes in the test that upstream's leaves to the umask, for the same reason, and its unsafe-runtime case uses world write (0666), because acfs-pkh accepts the owner's private-group write.
- acfs-fep: `test_fleet_runtime.py`, `test_fleet_runtime_git_snapshot.py` and `test_ubuntu_eol_repositories.py` set their fixtures' modes, for the same reason.
- acfs-pkh: the fleet tools (`acfs-fleet.py`, `swarm-fleet-*.py`, `swarm_fleet_probe.sh`) accept group write when the group is the user's own private group, so repositories made under Ubuntu's umask 0002 aren't refused; upstream refuses any group write (operator ruling, 2026-10-09). Upstream's `swarm-fleet-provision.py`, new in the 2026-10-10 sync, still refuses it: acfs-r39.
- acfs-a04: `ACFS_REPO_OWNER` defaults to the fork's owner, so the one-liner installs the fork, not upstream. For the same reason, `apps/web/lib/claude-code-web.ts` points the cloud setup script, and the `/cloud-agents` page's "README section" link (acfs-27n), at the fork. The provider guides' one-liners (`scripts/providers/hetzner.md`, `contabo.md`, `ovh.md`) and `hetzner-cloud-init.yml`'s `repo=` fetch the fork too (acfs-a4s).
- acfs-m3l: the support inventory fixture in `test_support_resource_profile.sh` probes at the current time, not upstream's 2099, which `swarm_inventory.sh` excludes as a future probe.
- acfs-xe3: `test_install_fetch_composition.sh`'s A6 resolves against the default owner, not upstream's.
- acfs-b0u: `security.sh` adds `--compressed` to upstream's identity request, because some hosts gzip anyway (antigravity, 2026-10-10).
- acfs-d91: the installer refuses Ubuntu 22.04 unless `--target-ubuntu=24.04|26.04` upgrades it first, and 22.04 is no longer an upgrade target (`install.sh`, `ubuntu_upgrade.sh`, `upgrade_resume.sh`, `preflight.sh`, their tests and CI's 22.04 job); upstream still installs on 22.04. Existing 22.04 installs keep running `acfs update`. The manifest's 22.04 branches (PostgreSQL's jammy PGDG) and the wizard's 22.04 image option, whose command upgrades it, stay as upstream's.
- acfs-yca: Docker is the opt-in module `tools.docker`, not part of `cli.modern`, which upstream installs by default. It takes Ubuntu's `docker-compose-v2` where apt offers it, because `docker-compose-plugin` exists only in Docker's own repository. dsr depends on the module.
- acfs-patg: `ubuntu-entrypoint.yml` runs `test_ubuntu_upgrade_main.py` as root in an `ubuntu:24.04` container, because its `PrivilegedCheckpointReadTests` refuses the runner, and upstream's job fails on every run.
- acfs-5f9: `AGENTS.md` drops upstream's "Morph Warp Grep" section: Warp Grep is a hosted service that needs a Morph account and API key, and neither ACFS nor upstream installs it (the operator, 2026-10-10).
- acfs-9ij4: three Installer CI fixes, because upstream's job fails on every run.
  - Every UBS install (manifest, `install.sh`, `acfs update`, the doctor's fix) passes `--skip-ast-grep`. Otherwise UBS's installer can install ast-grep's `sg` launcher as `~/.local/bin/ast-grep`, which runs itself until the system refuses. The doctor's fix also passes `--skip-hooks`, as the others already did.
  - The workflow YAML lints (`installer.yml`, `checksum-system-tests.yml`) warn on line length instead of failing.
  - `test_fresh_root_bootstrap_regression.sh` reads the checkout from `$REPO_ROOT`, not `/repo`.
- acfs-zbrk: repairs hosts that UBS already gave the `sg` launcher. `acfs update` moves a `~/.local/bin/ast-grep` that carries the launcher's deprecation banner aside, once `~/.cargo/bin/ast-grep` exists. The doctor's `tool.sg` fails on it without probing `sg`, which would start the loop. `stack.sh`'s `install_ubs` passes `--skip-hooks --skip-ast-grep`, as the manifest does.
- acfs-7is5: Installer CI's "Verify key tools" checks `agy`, the default agent, instead of the retired `gemini`, which upstream's job still runs and no install provides. `scripts/tests/lint_installer_verify_agents.sh`, run in the ShellCheck job, checks that list against the manifest's `enabled_by_default` agents.
- acfs-dy4f: `apps/web/e2e/production.spec.ts` checks the Claude Code cloud setup snippet in the form upstream's 8c0c027e renders (`printf '%s\n' "$acfs_cloud_setup" | bash`). Upstream's spec still expects the old `scripts/claude-code-web-setup.sh | bash`, so Production Smoke Tests fail against upstream's live site.
- acfs-hohp: the three desktop lesson-sidebar tests in `apps/web/e2e/learn.spec.ts` set a 1440×900 viewport. At the default 1280px, WebKit on Linux leaves its classic scrollbar out of the media-query width, so the page falls below `xl` and hides the sidebar, and Website CI's webkit job fails on every run.
- acfs-aec: when the installer copies root's `authorized_keys` into the target user's (`install.sh`'s `normalize_user` and `user.sh`'s `migrate_ssh_keys`, both through `user_merge_authorized_keys`), it compares keys by type and body. It skips a key the target already has, and copies a key found only on cloud-init's disable_root line without that line's forced command. Upstream copies by exact line, so the disable_root copy, which refuses the login, lands after the target's own copy.
- acfs-i9lz: CI's "Unit tests (bats)" workflow (`unit-bats.yml`) runs every `tests/unit/**/*.bats`, which no upstream workflow runs. `test_interactive_flag.bats` gives its tests their own global git config with an identity, because newproj commits only when git has one, so upstream's two commit tests fail under a throwaway HOME. `test_screens.bats` accepts `get_default_projects_dir`'s `/data/projects` fallback, which upstream's test predates, so it passes on a runner without `/data/projects`.
- acfs-6nqh: upstream's tests remove the temp dirs they create once they pass, where upstream's keep them. That covers the plugin, drift, architecture, readiness, profile and generate tests in `packages/manifest`, the fleet, cloud-setup and upgrade tests in `tests/unit`, `test_security.sh`, `ubuntu_upgrade_test.sh`, the VM harness's artifact dir, and the unit tests' `acfs-*-test-artifacts-*` dirs. Each still keeps its artifacts after a failure. `swarm-fleet-collect.py` writes its kept integration scratch under `$TMPDIR`, not a fixed `/tmp`.
- acfs-2iq: CI's "Checksum Drift" workflow (`checksum-drift.yml`) runs `scripts/checksum-drift-check.sh` once a day. The check compares every pin in `checksums.yaml` with what its URL serves now (`security.sh --verify --json`) and fails on drift, naming each stale pin; it never writes the file. Upstream keeps its pins fresh with `scripts/checksum-monitor-local.sh` instead, which commits and pushes the refresh to upstream's repository and which the fork doesn't run.
- acfs-c4m: the issue links in `scripts/lib/errors.sh`, in `security.sh`'s stale-pin hint and on `apps/web/app/troubleshooting/page.tsx` point at the fork's tracker; the hint also says ACFS, not upstream, refreshes the pin. The complete guide's link stays on upstream's tracker, because the sentence around it is upstream's author offering by name to answer questions there. `tests/unit/test_fork_source_defaults.sh` checks the website's issue links too.
- acfs-zic: `swarm_plan.sh` advises quiesce `scale_down` only for counts above the recommendation, not for every warning, so a warning within it proceeds with `launch_with_review`, and `acfs swarm launch --accept-warnings` can admit it. Upstream maps every warning to `scale_down`, which launch admission refuses, so the flag never admits anything there. `swarm-launch-admission.md` says so.
